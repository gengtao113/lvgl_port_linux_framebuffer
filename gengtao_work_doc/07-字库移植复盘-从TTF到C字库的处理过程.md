# 07 字库移植复盘：从「一个 TTF 文件」到「C 字库方案」的处理过程

> 目标工程：`lvgl_port_linux_framebuffer`
> 触发需求：把 `OPPO_Sans_4.0/OPPO Sans 4.0.ttf`（22MB 中文字体）移植进 LVGL 工程，用于显示中文
> 日期：2026-09-06
> 定位：这是**处理过程复盘**，记录「面对这个问题，我是怎么一步步分析、查证、决策、实测的」。具体操作步骤见 [06-移植OPPOSans中文字库](06-移植OPPOSans中文字库-离线转C字库.md)，本文与之互补。

---

## 一、任务与结论（先看结果）

**任务**：用户给了一个 22MB 的 TTF 中文字体，问「怎么移植到这个 LVGL 工程」。

**结论**：用 `lv_font_conv` 把 TTF **离线转成 LVGL 的 C 字库**，覆盖 GB2312 全字集（`0x4E00-0x9FA5` 共 20902 字），编译进 ELF，运行时零依赖显示中文。

**为什么不选 freetype 运行时加载**：当前工具链（Linaro 4.9.4）的 sysroot 里没有 freetype，硬走那条路要换工具链或交叉编译 freetype，成本远大于收益。

---

## 二、处理路径总览（按时间顺序，我实际做了什么）

```
① 摸清「字库是什么」
   → find 定位 TTF 文件，file/du 确认：22MB TrueType，含 CJK 全字集

② 摸清「目标工程现状」
   → 看 lv_conf.h：LVGL v8、LV_USE_FREETYPE=0、默认字体 montserrat_14（英文）
   → 看 main.c：目前只显示 FPS 数字，无中文
   → 看 lvgl/src/extra/libs/：已有 freetype/ 目录（但开关关着）

③ 摸清「工具链约束」（这一步决定了方案）
   → build_lvgl.sh 用 Linaro 4.9.4 arm-linux-gnueabihf-gcc
   → find 确认：Linaro sysroot 里【没有】freetype 头文件/库
   → find 确认：buildroot 工具链【有】freetype，但 ABI 与 Linaro 可能不匹配

④ 提出两条路线 + 列出对比表（freetype vs lv_font_conv）

⑤ 用 AskUserQuestion 让用户拍板两个关键决策点
   → 显示内容：中文动态文字（→ 需要全字集）
   → 移植方式：离线转 C 字库

⑥ 实测验证（不是拍脑袋估大小）
   → npx lv_font_conv --version 确认工具可用（1.5.3）
   → 后台实转一份：bpp=4 size=20 全 CJK → 81 秒，21MB
   → 后台实转 bpp=2 对比 → 63 秒，13MB

⑦ 用实测数据修正文档里的估算值

⑧ 产出：06 操作文档 + 本文复盘文档
```

## 三、关键决策与依据

### 决策 1：离线转 C 字库，而非 freetype 运行时加载

这是整个任务的核心岔路。判断依据不是「哪个更好」，而是「哪个在当前约束下成本最低」：

| 约束事实 | 对方案的影响 |
|---------|-------------|
| Linaro 4.9.4 sysroot 无 freetype | freetype 路线要换工具链 / 交叉编译 / 混用 buildroot 库（ABI 风险） |
| 工程是纯 C + CMake，已用「离线资源」模式（GIF 就是 A:/root/*.gif 这种外部文件） | 但 GIF 是运行时读文件，字库走离线编译进 ELF 更符合嵌入式惯例 |
| 需求是「显示中文」而非「任意矢量缩放」 | 字符集/字号固定即可满足，freetype 的「任意字号」优势用不上 |

**结论**：离线转 C 字库把「换工具链」这个大坑绕开了，代价（字号固定、字符集固定）在「显示中文」场景下可接受。

### 决策 2：字符集覆盖 GB2312 全字集，而非几个词

用户选「中文动态文字」= 运行时可能显示任意中文，不能只转「设置/返回」这几个词。所以用 `-r 0x4E00-0x9FA5` 覆盖整个 CJK 基本区，GB2312 的 6763 字全在内，任意常用中文都能查到字形。

> **落地时这个决策被反向验证了一次**：光有中文字库还不够——某个控件若不显式设中文字体，仍会用 LVGL 默认的 `montserrat_14`（**纯英文**，只有 ASCII 字形，没有「帧率/模式」这几个汉字），中文照样显示**方框**。FPS 那行加中文就踩了：`s_perf_label` 没设字体 → 方框。修复是给它单独设一份小号中文（`oppo_sans_14`）。所以「转中文字库」和「给每个中文 label 设中文字库」**缺一不可**。

### 决策 3：bpp 用 4（抗锯齿）

中文笔画密集，bpp=1 小字号会发虚。bpp=4 是 16 级灰度，效果最好；代价是体积大。所以把 bpp=2 作为「空间不够时」的降级选项，并实测了两者差多少（21MB vs 13MB），让用户有据可选。

## 四、查证的事实清单（哪些事实真正左右了方案）

复盘时发现，真正左右决策的不是「LVGL 支不支持 TTF」，而是下面这些**被主动查证**的事实：

1. **字库是什么**：`file` 确认 22MB TrueType 含 CJK → 中文场景，需要中文字库方案。
2. **LVGL 版本**：v8，`LV_USE_FREETYPE 0` 关着 → 走 freetype 要先开开关 + 链库。
3. **工具链没有 freetype**：`find` Linaro sysroot 无 `ft2build.h`/`libfreetype` → freetype 路线有硬障碍。
4. **lv_font_conv 可用**：`npx --version` 返回 1.5.3 → 离线路线工具就绪，无需安装。
5. **UTF-8 已开**：`lv_conf.h` 里 `LV_TXT_ENC LV_TXT_ENC_UTF8` → 中文字符串能直接进 label。

> 教训：如果一开始没查「工具链里到底有没有 freetype」，很容易默认「LVGL 自带 freetype，开个开关就行」，结果到交叉编译那步才卡住。**先查工具链，再定方案**。

## 五、实测数据（为什么值得花 3 分钟实转）

估算「一个全字集字库多大」很容易错——我最初的估算（2~4MB）和实测（21MB）差了 5 倍。所以必须实测：

| 实测项 | 结果 |
|--------|------|
| bpp=4 转换耗时 | 81 秒 |
| bpp=4 `.c` 大小 | 21MB（源码 hex 文本；编译后只读段实测 3.3MB） |
| bpp=2 转换耗时 | 63 秒 |
| bpp=2 `.c` 大小 | 13MB（编译后只读段约 2MB） |
| bpp 4→2 缩减 | 约 38%（不是减半，因 glyph 描述结构不变） |

**实测带来的纠正 1**：21MB 不是「编译进板子的体积」，是 `.c` 源码体积（hex 文本约 5 倍膨胀），编译回二进制后只读段实测 3.3MB。这个区分很重要——否则会误以为板子要扛 21MB 常驻内存。

**实测带来的纠正 2（编译验证才发现的坑）**：全字集字库编译会报 `#error "Too large font or glyphs..."`，必须开 `LV_FONT_FMT_TXT_LARGE 1`。这一步是「转换成功」看不出来的，只有「编译验证」才会逼出来。所以验证不能停在「转出 .c」，要到「编译通过」。

## 六、可复用的方法论（下次遇到类似问题照这个走）

把这次处理抽象成「往嵌入式工程移植一个第三方资源/库」的通用路径：

1. **先定「资源是什么」**：`find` + `file` + `du` 把源头的格式、大小、性质摸清（TTF？含 CJK？多大？）。
2. **再定「工程现状」**：版本、相关开关、当前用法（有没有已经能显示中文？用的什么字体？）。
3. **关键一步：查工具链/依赖约束**：目标工具链里有没有所需库？这是「选方案」的最大分水岭。
4. **列两条以上路线的对比表**：依赖 / 工具链改动 / 字符集 / 内存 / 集成方式，逐项比。
5. **把「用户必须拍板」的决策点抽出来问**，而不是替用户猜（显示什么内容、能不能接受固定字符集）。
6. **实测关键指标**：体积、耗时这类数字别靠估算，跑一次拿真值，再写进文档。
7. **产出两份文档**：一份「怎么做」（操作步骤），一份「为什么这么做 + 怎么想的」（复盘，即本文）。

## 七、落地后的补充（2026-09-06）

当初留的两个参数已定，整条链路也走完了：

1. **字号**：定了两个——正文/底部中文用 `oppo_sans_20`，FPS 小字用 `oppo_sans_14`（正好验证了「每字号转一份」）。
2. **bpp**：用 4（抗锯齿）。

走完「转 → 集成 CMake → main.c 加中文示例 → 交叉编译 → 上板」后，实际还踩了三个**配置/使用坑**（详见 [09](09-中文空白Debug复盘-压缩字库与LV_USE_FONT_COMPRESSED.md)）：

- `LV_FONT_FMT_TXT_LARGE`（编译期 `#error`，本文步 2 已记）；
- `LV_USE_FONT_COMPRESSED`（运行期**空白**：字库是压缩的，但没开解压）；
- 默认字体 `montserrat_14` 是纯英文（中文**方框**：见上文决策 2 的佐证）。
